# How this system is built: an agentic workflow

This codebase is developed and operated with [Claude Code](https://claude.com/claude-code)
as the primary engineering tool, with a human owner reviewing and directing.
This document describes the workflow concretely — what the agent does, what
stays human, and which guardrails make an autonomous process acceptable in a
system that moves real money.

## Division of labor

**Human-owned:** strategy and risk parameters, what to build next, security
policy decisions (the signer allowlist, what the policy engine may sign),
anything irreversible (deploys, key handling, making a repo public).

**Agent-owned:** implementation, test authorship, refactoring, debugging from
logs, documentation, and multi-step orchestration — including spawning
specialized subagents for parallel work (this repo's vitest migration ran as
three concurrent subagents with disjoint file ownership; the Rust signer
milestones ran the same way).

## The guardrail story

The interesting part of running an autonomous process against a funded wallet
is not the automation — it is the containment:

1. **Process isolation.** The bot builds unsigned transactions; only the signer
   daemon holds the key (encrypted at rest, interactive unlock). A bug — or a
   compromised dependency — in the 20k-line bot cannot exfiltrate the key.
2. **Policy as hard constraint.** Every transaction is deserialized and checked
   against a program allowlist, SPL-transfer destination rules, and
   simulation-based CPI discovery before signing. The agent can modify bot
   code freely; it cannot widen what gets signed without touching the signer,
   which is a reviewed trust boundary (see `CLAUDE.md`).
3. **Regression tests as memory.** Every production incident becomes a test
   (`docs/testing-notes.md` records their intents). The agent is instructed to
   treat test deletion as a recorded decision, not a cleanup.

This is the same shape as permission systems for AI agents in general: a
capable-but-fallible automated actor, a small enforced policy kernel, and a
human unlock step for the dangerous capability.

## Working practices that proved out

- **Golden vectors over reimplementation trust.** The Rust signer port is
  verified against fixtures generated by the *TypeScript implementation
  itself* — byte-identical signing, cross-implementation keyfile decryption —
  rather than against a human's reading of either codebase.
- **Mutation-checking new tests.** When the agent writes tests for existing
  code, it deliberately breaks the code under test and confirms the new tests
  fail, then restores byte-identically. Passing tests prove little otherwise.
- **Subagent fan-out with explicit file ownership.** Parallel subagents each
  get an exact file list; shared files (module roots, lockfiles, configs) are
  pre-staged by the orchestrator so no two agents write the same path.
- **Persistent memory.** Project facts that outlive a session — architecture
  decisions and their why, production gotchas, incident root causes — are
  written to a memory store the agent reloads each session, so lessons are not
  re-learned at incident speed.
- **Changelog discipline.** Every deploy is versioned in `CHANGELOG.md`; the
  entry is written by the agent as part of the change, not reconstructed later.
